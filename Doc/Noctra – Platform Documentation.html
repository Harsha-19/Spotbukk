SpotBukk – Platform Documentation

Event registration, payment, digital ticketing and QR check-in. Roles: Customer · Staff · Admin.

1. System overview

SpotBukk has a public/customer side and a protected operations side. Both meet at the QR ticket: customers receive it, staff scan it, the backend is the single authority that validates it.

2. Roles and access

2.1 Customer can

Sign up / log in · browse events · view event details · register · add attendees/guests · pay · receive a digital ticket · view ticket and QR · see registration and payment status · receive notifications · view booking history.

2.2 Customer must never see or reach

QR scanner · staff check-in interface · staff tools · admin dashboard · event management · payment management · analytics · other users' registrations.

2.3 Staff can

Scan ticket QR · enter ticket/booking code manually · see the attendee details needed for entry (name, pass type) · validate and check in · see "already used" · see invalid / expired / cancelled · view today's check-in activity.

2.4 Permission matrix (enforced by the backend)

Key rule: hiding UI is not security. Even if someone types https://SpotBukk.com/staff/check-in or calls the API directly, the server checks the authenticated account's role on every request and returns 401 (not logged in) or 403 (wrong role).

  E -- Yes --> F{Ticket exists and ISSUED?}

6. Redefined / added items

These fill gaps in the original notes:

Area Decision
Roles A single role on the account: CUSTOMER, STAFF, ADMIN. Staff accounts are created by admins only; no public staff signup.
Separate logins /staff/login and an admin login are distinct from the customer login, with stricter rate limits, shorter sessions and optional 2FA for admin.
Payment truth Confirm payment only from the gateway's signed webhook, never from the browser redirect. Use idempotency keys so retries cannot create duplicate tickets.
QR token Opaque, signed (HMAC/JWT) or random high-entropy token. Contains no personal data. Backend looks it up and verifies it; the QR alone never grants entry.
Double scan Check-in is one atomic update (UPDATE ... WHERE status='ISSUED') in a transaction, so two staff scanning at once cannot both succeed.
Two-step scan validate previews the result (read-only); check-in commits. Manual code entry uses the same path.
Staff scope Staff are assigned to specific events; they see only the data needed for entry.
Audit Every scan attempt (success or fail), staff ID, time, gate/device is logged.
Refunds / transfers Refund or cancellation sets the ticket to CANCELLED and invalidates its QR. Re-issue creates a new token and revokes the old one.
Offline venues Optional: pre-download signed ticket list for the event so the scanner survives poor connectivity, syncing check-ins afterward.

10. Security checklist

  • Role check middleware on every /staff/* and /api/staff/* route; default deny.
  • Ownership check on every customer resource (users only read their own tickets).
  • Hash QR tokens at rest; rate limit scan and login endpoints.
  • HTTPS only, secure httpOnly cookies, CSRF protection.
  • Webhook signature verification and idempotency.
  • Audit logs for all staff and admin actions.
