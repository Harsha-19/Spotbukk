SpotBukk – Server & Architecture Guide

A beginner-friendly explanation of what the server does, how domain, hosting and server differ, and how SpotBukk should be set up for the website now and a mobile app later.

1. What does a server actually do?

Think of the server as the engine room of the product. The customer's phone or browser is only the screen. The important data and rules live on the server.

Simple way to remember: the Angular website is the face, the backend is the brain, the database is the memory.
flowchart TB
  W[Website - Angular] --> I((Internet))
  A[Mobile app - Android / iOS] --> I
  I --> S[SERVER]
  S --> API[API: business logic]
  S --> DB[(Database: users, events, tickets, payments)]
  S --> SV[Services: payment, email, QR, notifications]

The server handles: user accounts and login, events, registrations, ticket generation, payments, QR validation, staff check-ins, admin work, emails and notifications, analytics, database access, security and business rules.

2. Does the server host the website too?

Yes, but that is only one of its jobs. A server runs several pieces side by side.

flowchart TB
  D[Domain: SpotBukk.in] --> N[DNS]
  N --> S[Server]
  S --> W[Website]
  S --> A[Backend API]
  S --> DB[(Database)]
  S --> F[File / image storage]
  S --> B[Background services]

SpotBukk.in can show the website and api.SpotBukk.in can be the backend API. The Angular site then talks to https://api.SpotBukk.in.

3. One backend for the website and the future app

Do not build one backend for the website and another for the app. Build one API and let every front end use it.

flowchart LR
  W[Website - Angular] --> API[SpotBukk API]
  M[Mobile app - Android / iOS] --> API
  API --> DB[(Database)]

Both share the same users, events, registrations, payments, tickets, QR codes, staff, admin, notifications and database. When the app arrives later, authentication, tickets, payments, QR and admin do not need to be rebuilt. The app simply uses the existing API. This is why the backend should never be designed around Angular.

4. Domain vs hosting vs server

These three get mixed up a lot.

Term Meaning Example
Domain The address people type into the browser SpotBukk.in
Hosting provider The company that gives you the server and infrastructure A cloud company that rents you a VPS
Server The computer that runs your software Ubuntu Linux VPS, 4 CPU, 8 GB RAM, 160 GB SSD 
flowchart LR
  A[Domain: SpotBukk.in] --> B[Hosting provider]
  B --> C[Server / VPS]
  C --> D[SpotBukk: website, API, database, services]

5. What server should SpotBukk start with?

Keep it simple at first. You do not need a huge server on day one; the final size depends on expected traffic, database size, image storage and payment volume. Leave room to scale.

Item Initial recommendation
OS Ubuntu LTS
CPU / RAM 4 vCPU / 8 GB
Storage 160+ GB SSD or NVMe
Network Public IPv4 (IPv6 optional)
Docker Latest stable version
Database PostgreSQL
Reverse proxy Nginx or equivalent
Deployment Docker Compose to start
Must have HTTPS, firewall, backups, monitoring

6. What software runs on the server?

flowchart TB
  U[Ubuntu Linux] --> D[Docker]
  D --> RP[Reverse proxy - Nginx]
  D --> FE[Angular frontend]
  D --> BE[Backend API]
  D --> PG[(PostgreSQL)]
  D --> RD[(Redis - optional)]
  D --> WK[Background workers]

Why Docker? Each part runs in its own isolated container, so the frontend, API and database stay separate and are easier to update. Docker Compose can start the whole set with one command on a single server.

7. What is a reverse proxy?

It is the front door. Nginx sits first and decides where each request goes.

flowchart TB
  I((Internet)) --> N[Nginx / reverse proxy]
  N -- SpotBukk.in --> FE[Angular app]
  N -- api.SpotBukk.in --> API[Backend API]
  API --> DB[(PostgreSQL)]

It handles incoming requests, HTTPS/TLS, routing, forwarding API calls, serving the Angular files, security headers and connections. Only the proxy is exposed to the internet, never the database.

8. Where does the database live?

At first, on the same server. The backend talks to it over a private network, and the database is never opened to the internet.

flowchart LR
  subgraph Public
    N[Nginx]
  end
  subgraph Private network
    BE[Backend] --> PG[(PostgreSQL)]
  end
  N --> BE

If SpotBukk grows, the database can move to a dedicated managed database server.

9. What about images and uploads?

SpotBukk will have event posters, venue photos, artist images, profile pictures and ticket assets. Decide early not to keep all of them on the application server forever. Use separate object/file storage, which can later be served through a CDN.

flowchart LR
  subgraph Server
    A[Application]
    D[(Database)]
  end
  subgraph Object storage
    E[Event images]
    V[Venue images]
    O[Other uploads]
  end
  A --> E
  A --> V
  A --> O

10. Which ports should be public?

This is very important. Only web traffic should reach the server from outside.

flowchart LR
  I((Internet)) -- 80 HTTP --> N[Nginx]
  I -- 443 HTTPS --> N
  N --> FE[Frontend]
  N --> BE[Backend]
  I -. blocked .-> X1[PostgreSQL 5432]
  I -. blocked .-> X2[Redis 6379]
  I -. blocked .-> X3[Backend 3000]
  I -. blocked .-> X4[Database admin ports]

Keep database, Redis, backend and admin ports private unless there is a very specific, secured reason to open one.

11. The final target architecture

flowchart TB
  I((Internet)) --> FW[Firewall]
  FW --> N[Nginx]
  N --> FE[Frontend - Angular on SpotBukk.in]
  N --> API[Backend API on api.SpotBukk.in]

  API --> WK[Workers]
  WK --> EM[Email / notifications]
  API --> OS[Object storage: event images and media]
  M[Mobile app] -. same API .-> API

12. Domain setup

Address Purpose
SpotBukk.in and www.SpotBukk.in Public website
api.SpotBukk.in Backend API (website and app both use it)
SpotBukk.in/admin, SpotBukk.in/staff Admin and staff areas, protected by backend authorization

Separate admin.SpotBukk.in or staff.SpotBukk.in are possible, but not required. For the client, keeping one public address is simpler.

13. How to set it up, step by step

flowchart TB
  S1[1. Buy domain] --> S2[2. Buy VPS]
  S2 --> S3[3. Secure the server]
  S3 --> S4[4. Install Docker + Compose]
  S4 --> S5[5. Deploy the application: docker compose up -d]
  S5 --> S6[6. Deploy PostgreSQL with persistent storage]
  S6 --> S7[7. Deploy backend API]
  S7 --> S8[8. Deploy Angular via Nginx]
  S8 --> S9[9. Point DNS to server IP]
  S9 --> S10[10. Enable HTTPS]
Step Details
1. Domain Buy something like SpotBukk.in.
2. VPS Ubuntu LTS, 4 vCPU, 8 GB RAM, 160+ GB SSD, public IP.
3. Secure SSH keys, firewall, non-root deploy user, automatic security updates, Fail2ban/rate limiting, backup plan.
4. Docker Install Docker and Docker Compose.
5. Deploy Run the stack with docker compose up -d.
6. Database PostgreSQL with persistent storage.
7. Backend Start the backend API container.
8. Angular Build to static files and serve them through Nginx.
9. DNS Point SpotBukk.in and api.SpotBukk.in to the server IP.
10. HTTPS Enable for both. No login or payment system should ever run on plain HTTP.
Remember: a container is not a backup. Containers are temporary. PostgreSQL needs persistent storage and a separate, tested backup strategy.

14. The big takeaway

flowchart TB
  B[SpotBukk BACKEND - REST API] --> A[Angular website]
  B --> AN[Android app]
  B --> IO[iOS app]

Design the backend around the API, not around Angular. Authentication, events, registrations, payments, tickets, QR, staff, admin and analytics are built once and reused by every client.

Quick glossary

Word Plain meaning
API The set of doors the website or app uses to ask the server for things
DNS The phone book that turns SpotBukk.in into the server's IP address
VPS A rented virtual computer in a data center
Docker A tool that runs each part of the app in its own box
Reverse proxy The front door that routes visitors to the right part
HTTPS Encrypted web traffic, the padlock in the browser
Redis A fast temporary store, useful for caching and queues
Object storage A separate place for images and files
